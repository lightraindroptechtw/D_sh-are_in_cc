# CC 版原插件畫面移植與驗證

日期：2026-10-28。修改對象是已登記的 `d-sh-are-in-cc` 市場來源，不是工作資料夾裡的舊副本。CC 插件版本更新為 0.2.0；根目錄 package.json 的 0.4.0 是原有內部套件版本，這次沒有將它當作 CC 發行版本。

## 做了什麼

| 項目 | 改動 |
|---|---|
| 設定頁、資料館、主頁與浮窗 | 打包原始前端與資源，以共用網頁環境載入，保留原始檔雜湊與授權 |
| 開啟方式 | 每個轉換後插件提供 `/<插件名稱>-ui` 指令，呼叫 CC 的內建瀏覽器；失敗時顯示本機網址 |
| 原後端 | 畫面請求轉到原插件已登記的本機路由；支援一般網頁請求、表單、二進位資料與串流 |
| 設定保存 | 接到真正的 DSH 設定服務；底層更新成功才回報保存成功 |
| 畫面呼叫工具 | 交回 CC 版原有的工具處理流程，沿用已辨識發文工具的確認、限制、通知和遮蔽 |
| 取消操作 | 關頁或取消網頁請求會傳到 CC 模組；晚到的確認不能重新啟動尚未執行的工具 |
| 沒有後端的純前端插件 | 仍可封裝與開啟；不建立假的後端服務，缺少功能會明確列出 |
| 安裝與審查說明 | 不再把所有有畫面的插件一律說成「裝不進」；審查報告與生成說明列出開頁方法 |
| 原插件辨認自己的設定 | 讓原插件看見原本的載入名稱，保留真正的執行實例與設定資料 |

聊天外觀、原聊天卡片和改寫 CC 自身介面不在範圍內。DSH 專用元件、未接上的服務與 WebSocket（雙向持續連線）升級代理仍可能無法使用。這不是完整 DSH 桌面環境。

## 怎麼測 CC，而不額外請模型工作

1. 使用電腦上真正的 CC 2.1.309 執行 `claude plugin test`。這是 CC 自帶的模組測試環境，模型、子代理、瀏覽器與確認視窗等外部動作由測試資料回覆，不呼叫付費模型。能證明 CC 接受這些事件與回傳格式，但不等於已操作真正的桌面瀏覽器。
2. 真正啟動 CC 版的 Node（程式執行環境）子程序，跑官方 DSH 服務和原插件。用本機 HTTP（網頁請求）測設定、路由、保存與關閉。
3. 最後才是 CC 桌面端實際載入、開瀏覽器與點擊。這一層本次尚未完成，不能拿其他瀏覽器或測試替身的結果代替。

三個原插件的詳細資料在 `validation/summary.md`，機器可讀結果在 `validation/cc-backend-results.json` 和 `validation/native-package-validation.json`。它們的保存測試走原插件自己的設定／資料 API；三者都沒有 DSH 設定命名空間，所以不把它們算作 DSH settings.update 的真實插件測試。後者另用合成插件實際寫入驗證。

AI Library 預先建立了清楚標示的本機館藏測試資料，避免自動同步市場。沒有登入、呼叫模型、讓子代理執行工作或真正對外發文。

## 使用與邊界

- 之後重新轉換的插件才會附上這次畫面支援；現有的第三方轉換產物不會自動改寫。
- 已啟動的 CC 工作階段／市場程序需要重新載入，才會使用更新的轉換器。沒有為此中斷使用者正在進行的其他工作。
- 已用 CC 原生 `plugin update` 將使用者安裝從 0.1.0 更新至 0.2.0；五個主要執行檔的來源／安裝快取雜湊相同。CC 回報需重啟才能生效。
- 已辨識的工具操作會回到原有確認流程；第三方插件自己寫的 HTTP 路由，不能保證其中每個行為也都變成發文工具確認。文件已明確限定保護範圍。
- 目前的 CC 詢問介面沒有在使用的型別中提供關閉既有詢問視窗的取消參數；本次會停止等待並忽略晚到回答。已開始的工具是否能立即停止，仍取決於原插件的取消支援；不會回滾已發生的副作用。
- 修改前的檔案備份在本資料夾的 `backups/`。生成的測試模板可由備份的原模板重新生成。
